# Personal Data Store

## CRITICAL: Database Safety

Never run any of the following against this database:
- `DROP TABLE`, `DROP SCHEMA`, `DROP DATABASE`
- `TRUNCATE`
- `DELETE` without a `WHERE` clause
- `drizzle-kit push` (any flag), `drizzle-kit drop`, `drizzle-kit reset`
- Any ad-hoc SQL that wipes or recreates tables

Always use migrations (`db:generate` → `db:migrate`). Always import with `.onConflictDoNothing()` (or an explicit `ON CONFLICT` rule). If a destructive operation seems necessary, stop and ask the user first — assume the answer is no.

## /api/about — Unified Discovery

`GET /api/about?topic=<string>&limit=<n>` (default 5, max 20, auth required).

Fans out in parallel to the documents semantic-search index and every domain table that plausibly matches the topic. Always returns the same shape with all keys present (empty arrays when nothing matches):

```json
{
  "documents": [...],   // semantic search over embeddings
  "health":    [...],   // health_metrics by metric_type ILIKE
  "workouts":  [...],   // workouts by name ILIKE
  "finance":   [...],   // yield_positions, transactions, subscriptions ILIKE
  "genomics":  [...],   // genomics_variants by gene/rsid ILIKE
  "business":  [...],   // clients/projects by name ILIKE
  "analyses":  [...]    // analyses by title/summary ILIKE
}
```

Use this as the first call when asked about Oak's data on any topic before reasoning from memory.

## `source` Convention on documents and analyses

Both `documents` and `analyses` have a nullable `source text` column. Use it to track provenance:

- `"oak"` — information provided directly by Oak (preferences, positions, facts)
- `"claude"` — generated by Claude (analyses, drafts, recommendations)
- `"import:<connector>"` — imported by a connector (e.g. `"import:gmail"`, `"import:revolut"`)
- `null` — legacy data imported before this column existed

Always set `source` when creating new documents or analyses.

## Canonical Documents

Documents may be tagged with `canonical_for: text[]` — a list of topic slugs (e.g. `fitness.strength`, `goals.cardiovascular`) that mark them as authoritative reference material for those areas.

**Before any analysis task that touches a goal area, call `GET /api/canonical?topics=<slug>,<slug>` and ground the analysis in the returned content.** If no canonical doc exists for the area, state that explicitly in the response rather than reasoning unaided from memory.

Topic slugs use dot notation: `<area>.<subarea>` (e.g. `fitness.strength`, `fitness.muscle_growth`, `goals.cardiovascular`). Pick the most specific slugs that match your task; the endpoint OR-matches across the array.

The endpoint returns full document content — quote and cite by title, don't summarise blindly. Canonical documents are auto-chunked and embedded on insert/update via `chunkAndEmbed`, so they also surface through `/api/about` and semantic search.

To mark a document canonical, POST/PATCH `/api/documents` with `canonicalFor: ["topic.slug", ...]`.

## Inbox Pattern

Documents with `domain: "inbox"` are a catch-all for unclassified content. Use this domain when POSTing information that needs human review before being promoted to a proper domain.

The inbox triage UI at http://localhost:3001/inbox lists `domain='inbox'` documents and offers Promote (edit `domain` and `type`, save via `PATCH /api/documents/:id`) and Delete (`DELETE /api/documents/:id`).

When writing information to PDS from a conversation:
1. If the domain and type are clear → POST directly to the right domain
2. If uncertain → POST to `domain: "inbox"` with `source: "claude"` and let Oak triage
